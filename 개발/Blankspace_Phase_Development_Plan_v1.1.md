# 0. 문서 목적 및 공통 개발 원칙

본 문서는 Blankspace의 개발을 Phase 0부터 Phase 10까지 나누어 정의한다.
각 Phase는 목표, 작업 범위, 세부 요구사항, 완료 기준, 검증 항목을
포함한다.

## 0.1 제품 목표

Blankspace는 개인 창작자가 게임 기획, 캐릭터 제작, 세계관 구축, 3D
모델링, 레퍼런스 수집 등의 창작 활동을 하나의 환경에서 수행할 수 있도록
지원하는 개인용 통합 창작 플랫폼이다.

사용자는 웹과 데스크톱에서 동일한 프로젝트 및 문서에 접근하고,
문서·컴포넌트·템플릿·시각화 도구·창작 자료를 자유롭게 구성하고 연결할 수
있어야 한다.

## 0.2 확정된 제품 방향

  항목               방향
  ------------------ -----------------------------------------------
  서비스 유형        개인용 창작 작업 플랫폼
  사용 환경          웹 + 데스크톱
  사용자 구조        개인 사용자 중심
  Workspace          사용자당 하나
  Project            다중 프로젝트
  데이터 저장        클라우드 중심
  백업               자동 클라우드 백업
  핵심 우선순위      창작 기능과 자유도
  다중 사용자 협업   초기 범위 제외
  웹·데스크톱 기능   가능한 범위에서 공통 기능 및 데이터 규격 공유

## 0.3 공통 설계 원칙

1.  창작 기능과 사용자 자유도를 우선한다.
2.  웹과 데스크톱은 동일한 데이터 규격과 공통 창작 기능을 사용한다.
3.  플랫폼 고유 기능은 공통 창작 시스템과 분리한다.
4.  템플릿 정의와 생성된 문서의 실제 콘텐츠를 분리한다.
5.  공통 컴포넌트는 공유 라이브러리로 관리한다.
6.  시각화 도구는 독립적인 편집 시스템으로 설계한다.
7.  문서와 에셋은 참조 관계로 연결하며, 참조 중인 파일을 임의로 삭제하지
    않는다.
8.  저장 성공은 실제 저장 완료를 의미해야 한다.
9.  클라우드 동기화와 백업은 별개의 기능으로 관리한다.
10. 기존 프로젝트의 데이터와 식별자를 임의로 삭제하거나 변경하지 않는다.
11. 구현되지 않은 기능을 완료된 것처럼 표시하지 않는다.
12. 각 Phase 완료 후 검증과 결과 보고를 진행하고, 대규모 다음 단계로
    넘어가기 전에 승인을 받는다.

## 0.4 용어

-   **Workspace:** 사용자의 전체 작업 환경. 사용자당 하나를 기본으로
    한다.
-   **Project:** 하나의 창작 활동이나 작업 단위를 관리하는 공간.
-   **Folder:** 프로젝트 내부 자료를 분류하는 계층 구조.
-   **Document:** 실제 콘텐츠 작업이 이루어지는 기본 단위.
-   **Template:** 문서 생성 시 기본 구조와 컴포넌트 구성을 제공하는
    정의.
-   **Component Definition:** 컴포넌트 종류와 기본 동작을 정의하는 공통
    규격.
-   **Component Instance:** 특정 문서에 실제로 배치된 컴포넌트와 그
    콘텐츠.
-   **Asset:** 이미지, 영상, 오디오 및 일반 파일.
-   **Sync:** 웹과 데스크톱 사이에서 변경 사항을 전달하고 일치시키는
    기능.
-   **Backup:** 특정 시점의 데이터를 별도로 보존하여 복구할 수 있도록
    하는 기능.

# Phase 0. 기존 프로젝트 분석

## 0.1 목표

기존 Blankspace 프로젝트의 코드, UI, 데이터 구조 및 구현 상태를
파악한다. 기존 기능을 무조건 유지하거나 처음부터 다시 만드는 대신 재사용
가능 영역과 개선 필요 영역을 구분한다.

**이 단계에서는 승인 없이 코드를 수정하거나 기존 데이터를 초기화하지
않는다.**

## 0.2 작업 범위

### A. 프로젝트 구조 분석

-   전체 폴더 및 파일 구조 확인
-   사용 중인 프레임워크와 라이브러리 확인
-   웹 애플리케이션의 진입점 및 주요 모듈 확인
-   빌드, 실행, 배포 방식 확인
-   환경 변수 및 외부 서비스 의존성 확인

### B. 기존 UI 분석

-   메인 화면과 사이드바 구조 확인
-   프로젝트 및 폴더 탐색 흐름 확인
-   문서 화면과 편집기 구조 확인
-   모달, 메뉴, 토스트 등 공통 UI 확인
-   반응형 및 다크 모드 구현 상태 확인

### C. 데이터 구조 분석

-   Workspace, Project, Folder, Document 구조 확인
-   문서 콘텐츠와 컴포넌트 저장 방식 확인
-   템플릿과 실제 문서 데이터의 분리 여부 확인
-   내부 링크 및 역링크 저장 방식 확인
-   이미지와 첨부 파일 저장 위치 및 참조 방식 확인
-   기존 ID 및 데이터 마이그레이션 가능성 확인

### D. 기능 상태 분류

각 기능을 다음 상태로 구분한다. - 구현 완료 - 부분 구현 - 미구현 - 오류
또는 불안정 - 중복 구현 - 재사용 가능 - 구조 변경 필요

### E. 데이터 보존 계획

-   기존 데이터 백업 가능 여부 확인
-   기존 ID 보존 범위 확인
-   데이터 구조 변경 영향 분석
-   마이그레이션이 필요한 항목 식별
-   복구 절차 수립

## 0.3 산출물

1.  기존 프로젝트 구조 분석서
2.  기술 스택 및 의존성 목록
3.  기존 UI 및 사용자 흐름 분석서
4.  기능별 구현 상태표
5.  데이터 구조 분석서
6.  재사용·개선·교체 대상 목록
7.  기존 데이터 보존 및 마이그레이션 계획

## 0.4 완료 기준

-   현재 프로젝트를 정상 실행할 수 있는 방법이 확인되어야 한다.
-   주요 기능의 구현 상태가 분류되어야 한다.
-   데이터 저장 위치와 구조가 확인되어야 한다.
-   기존 데이터 보존 방안이 마련되어야 한다.
-   다음 단계의 설계에 필요한 위험 요소가 문서화되어야 한다.

## 0.5 검증 및 승인

Phase 0 결과를 검토하고, 기존 구조를 유지할 영역과 변경할 영역을
승인받은 뒤 Phase 1로 진행한다.

## 1.3 웹·데스크톱 공통 구조

### 공통으로 관리할 기능

-   Workspace 및 Project 관리
-   Folder 및 Document 관리
-   문서 편집 엔진
-   컴포넌트 라이브러리
-   템플릿 시스템
-   시각화 도구의 데이터 규격
-   내부 링크 및 검색 규칙
-   사용자 지정 및 디자인 규칙

### 플랫폼별로 분리할 기능

-   운영체제 파일 선택 및 저장 경로 접근
-   데스크톱 설치 및 업데이트
-   운영체제 알림 및 창 관리
-   브라우저 기반 인증 및 세션 처리
-   플랫폼별 파일 권한 및 다운로드 처리

공통 창작 기능을 플랫폼별로 중복 구현하지 않는다. 플랫폼 고유 기능은
별도 어댑터 또는 인터페이스를 통해 연결한다.

## 1.4 기술 선택 검토

기존 프로젝트 분석 결과를 기준으로 최종 기술을 결정한다. 아래는 신규
설계 시 검토할 후보이며 확정 기술이 아니다.

  영역           검토 방향
  -------------- ------------------------------
  웹             React + TypeScript 검토
  데스크톱       Tauri 또는 Electron 비교
  공통 UI        공유 컴포넌트 및 편집 엔진
  API            서버 API 구조
  데이터베이스   PostgreSQL 검토
  파일 저장      S3 호환 Object Storage 검토
  인증           개인 사용자 인증
  배포           웹 호스팅 및 데스크톱 패키징

기술 선택 시 기존 코드 재사용성, 편집기 라이브러리 호환성, 파일 처리
요구사항, 유지보수 난이도를 비교한다.

## 1.5 데이터 구조 설계

주요 데이터: 1. User 2. Workspace 3. Project 4. Folder 5. Document 6.
Template 7. Component Definition 8. Component Instance 9. Design Preset
10. Asset 11. Document Link 12. Document Version 13. Backup Snapshot 14.
User Settings

각 데이터의 소유 관계, ID, 생성 및 수정 시각, 삭제 상태, 버전 정책을
정의한다. 모든 데이터에 동일한 필드를 무조건 적용하지 않고 데이터 종류에
맞게 설계한다.

## 1.6 시스템 간 경계 정의

-   Template은 기본 구조와 스타일 정의를 관리한다.
-   Document는 실제 콘텐츠와 문서별 구성을 관리한다.
-   Component Definition은 컴포넌트의 종류와 기본 규격을 관리한다.
-   Component Instance는 문서에 배치된 실제 컴포넌트 데이터를 관리한다.
-   Asset은 실제 파일과 메타데이터를 관리한다.
-   Document Link는 문서 사이의 참조 관계를 관리한다.
-   Visual Tool은 독립 편집 데이터를 가지되 문서와 에셋을 참조할 수
    있다.
-   Sync와 Backup은 서로 다른 책임을 가진다.

## 1.7 산출물

1.  전체 시스템 아키텍처
2.  웹·데스크톱 공통 기능 정의서
3.  플랫폼별 기능 분리표
4.  기술 스택 비교 및 선정 근거
5.  데이터 관계도
6.  시스템별 책임과 인터페이스 명세
7.  주요 데이터 및 ID 규칙

## 1.8 완료 기준

-   모든 핵심 시스템의 책임이 구분되어야 한다.
-   웹과 데스크톱이 공유할 데이터 규격이 정의되어야 한다.
-   Template, Document, Component, Asset의 경계가 명확해야 한다.
-   기술 선택의 근거와 미확정 사항이 기록되어야 한다.

# Phase 2. 데이터 및 클라우드 기반

## 2.1 목표

개인 Workspace의 데이터를 클라우드에 안전하게 저장하고, 웹과
데스크톱에서 공통으로 접근할 수 있는 기반을 구축한다.

이 단계에서는 창작 기능을 본격적으로 확장하기 전에 데이터 저장, 파일
저장, 인증, 동기화의 최소 기반을 마련한다.

## 2.2 개인 사용자 및 인증

-   개인 사용자 인증 방식 구현
-   사용자 소유 Workspace 연결
-   사용자별 데이터 접근 범위 제한
-   세션 관리
-   로그아웃 및 재인증
-   계정 복구 정책 검토

다중 사용자 협업, 프로젝트 공유, 역할별 권한 시스템은 초기 범위에서
제외한다.

## 2.3 클라우드 데이터베이스

-   Workspace 및 Project 기본 데이터 저장
-   Folder 및 Document 메타데이터 저장
-   데이터 ID와 소유 관계 관리
-   생성 및 수정 시각 관리
-   데이터 버전 관리 기반 마련
-   삭제 상태 및 휴지통 메타데이터 관리

## 2.4 클라우드 에셋 저장

-   이미지 업로드 및 조회
-   영상 및 오디오 파일 업로드 정책
-   일반 파일 업로드 및 다운로드
-   파일 메타데이터 저장
-   파일 고유 ID 관리
-   업로드 진행 상태 표시
-   업로드 실패 및 재시도
-   파일 참조 관계 관리
-   참조 중인 파일의 임의 삭제 방지

실제 파일 바이너리와 문서 콘텐츠는 분리하여 관리한다.

## 2.5 자동 저장 기반

-   변경 사항 감지
-   저장 대기 상태 관리
-   저장 요청 중복 방지
-   저장 성공 및 실패 상태 관리
-   서버 저장 완료 확인
-   새로고침 및 재접속 시 최신 데이터 복원

저장 성공 표시는 실제 서버 저장 완료를 확인한 뒤에만 표시한다.

## 2.6 동기화 기반

-   클라이언트 변경 사항 식별
-   서버 버전 확인
-   변경 사항 전송
-   서버 반영 결과 수신
-   동기화 상태 표시
-   실패한 요청 재시도
-   중복 요청 방지

초기에는 실시간 협업을 구현하지 않는다. 웹과 데스크톱 사이의 개인 데이터
동기화를 우선한다.

## 2.7 충돌 처리 원칙

-   수정 시각만으로 충돌 여부를 판단하지 않는다.
-   서버 버전 또는 변경 버전을 기준으로 충돌을 감지한다.
-   충돌 발생 시 한쪽 데이터를 자동으로 덮어쓰지 않는다.
-   충돌 데이터의 별도 보존 방식을 마련한다.
-   사용자가 비교하고 선택할 수 있는 복구 흐름을 설계한다.

## 2.8 백업 기반

-   Workspace 전체 백업 대상 정의
-   문서 및 프로젝트 데이터 백업
-   연결된 에셋 파일 백업
-   백업 시점 및 식별자 기록
-   백업 성공 여부 검증
-   백업 실패 알림 및 재시도
-   수동 백업 실행 경로 마련

백업 보존 기간과 실행 주기는 저장 용량 및 비용 검토 후 확정한다. 하루
1회 자동 백업은 초기 검토안으로 사용할 수 있으나 확정 정책은 아니다.

## 2.9 동기화와 백업의 구분

  항목        동기화                   백업
  ----------- ------------------------ --------------------------
  목적        최신 데이터 공유         과거 데이터 복구
  실행        변경 발생 시             정해진 주기 또는 수동
  대상        변경된 데이터            특정 시점의 데이터 집합
  복구        다른 클라이언트에 반영   이전 시점으로 복구
  실패 처리   재시도 및 충돌 처리      백업 실패 기록 및 재실행

## 2.10 산출물

1.  개인 인증 시스템
2.  클라우드 데이터 저장 기반
3.  클라우드 에셋 저장 기반
4.  자동 저장 모듈
5.  동기화 기본 모듈
6.  충돌 감지 정책
7.  백업 기본 모듈
8.  저장 및 파일 접근 보안 정책

## 2.11 완료 기준

-   개인 사용자 인증이 작동해야 한다.
-   사용자 Workspace 데이터가 클라우드에 저장되어야 한다.
-   웹과 데스크톱 클라이언트가 동일한 데이터 규격을 사용해야 한다.
-   파일 업로드와 참조 관계가 유지되어야 한다.
-   저장 성공과 실패가 정확히 표시되어야 한다.
-   백업 실행 결과를 확인할 수 있어야 한다.

# Phase 3. Workspace 및 문서 관리 시스템

## 3.1 목표

사용자의 전체 창작 자료를 프로젝트와 폴더 중심으로 관리할 수 있는 기본
공간 구조를 구현한다.

## 3.2 Workspace

-   사용자당 하나의 Workspace
-   Workspace 생성 및 전환 기능은 제공하지 않음
-   여러 Project 관리
-   Workspace 통합 휴지통
-   사용자 설정 연결

## 3.3 Project

-   프로젝트 생성 및 삭제
-   이름과 설명 수정
-   아이콘 설정
-   커버 이미지 설정
-   색상 설정
-   즐겨찾기
-   정렬
-   프로젝트 복제
-   프로젝트 내부 문서 및 폴더 관리

### 프로젝트 복제 규칙

복제 대상: - 프로젝트 정보 - 폴더 및 하위 폴더 - 문서 및 문서 콘텐츠 -
컴포넌트 구성 - 스타일 및 디자인 설정 - 이미지와 첨부 파일 - 프로젝트
내부 연결 관계

복제 시 새로운 Project ID, Folder ID, Document ID를 발급한다. 복제본
내부의 문서 링크는 복제본 내부의 대응 문서를 참조하도록 한다. 원본은
영향을 받지 않아야 한다.

## 3.4 Folder

-   프로젝트 최상위 폴더 생성
-   하위 폴더 생성
-   깊이 제한 없는 계층 구조
-   폴더 내부 문서 생성
-   문서와 하위 폴더 혼합 배치
-   폴더 이름 및 아이콘 변경
-   커버 이미지와 색상 설정
-   이동 및 복제
-   정렬
-   접기 및 펼치기
-   폴더 경로 표시

### 폴더 삭제

-   폴더와 모든 하위 폴더를 함께 휴지통으로 이동
-   내부 문서와 자료의 원래 위치 정보 보존
-   복원 시 기존 구조 복원
-   원래 위치가 없으면 복원 위치 지정

### 폴더 복제

-   복제본에 새로운 폴더 및 문서 ID 발급
-   복제본 내부 문서 링크는 대응 복제 문서를 참조
-   원본 폴더와 원본 문서는 변경하지 않음

## 3.5 Document 위치 및 관리

-   프로젝트 최상위에 문서 생성
-   폴더 내부에 문서 생성
-   문서 생성 및 삭제
-   문서 이름 변경
-   아이콘 및 커버 이미지 설정
-   설명 수정
-   이동 및 복제
-   즐겨찾기
-   정렬
-   태그 관리
-   문서 검색

문서는 기본적으로 동일 프로젝트 내부에서 이동한다. 다른 프로젝트로 직접
이동하는 기능은 초기 범위에서 제공하지 않는다.

## 3.6 문서 복제

-   문서 유형 복제
-   템플릿 구조 복제
-   컴포넌트 구성과 콘텐츠 복제
-   이미지 및 미디어 참조 복제
-   디자인 설정 복제
-   태그 및 설명 복제
-   복제본에 새로운 Document ID 발급

단일 문서 복제 시 내부 링크는 기본적으로 원본 문서를 참조한다. 프로젝트
또는 폴더 전체 복제 시에는 복제본 내부의 대응 문서를 참조한다.

## 3.7 휴지통

관리 대상: - 프로젝트 - 폴더 - 하위 폴더 - 문서 - 기타 삭제된 자료

기능: - 삭제 날짜 표시 - 원래 소속 프로젝트 표시 - 원래 폴더 경로 표시 -
개별 복원 - 일괄 복원 - 영구 삭제 - 휴지통 비우기 - 삭제된 폴더의 하위
구조 확인

복원 시 기존 ID와 위치를 유지한다. 원래 위치가 존재하지 않으면 복원
위치를 지정하도록 한다.

## 3.8 산출물

1.  Workspace 관리 화면
2.  Project 관리 기능
3.  Folder 트리 및 관리 기능
4.  Document 목록 및 관리 기능
5.  통합 휴지통
6.  이동 및 복제 로직
7.  삭제 및 복원 테스트

## 3.9 완료 기준

-   프로젝트와 폴더 구조를 생성하고 수정할 수 있어야 한다.
-   문서를 프로젝트 최상위 또는 폴더 내부에 생성할 수 있어야 한다.
-   이동 및 복제 규칙이 지켜져야 한다.
-   삭제된 자료의 원래 위치와 ID가 보존되어야 한다.
-   복원 후 기존 연결이 정상 작동해야 한다.

# Phase 4. 문서 편집 엔진

## 4.1 목표

문서 유형별 편집 방식은 구분하되 문서 관리와 데이터 저장 기반은
공유한다.

## 4.2 문서 유형

### A. 템플릿 문서

-   미리 정의된 템플릿을 기반으로 생성
-   템플릿의 기본 컴포넌트 구성 사용
-   생성 이후 문서별로 독립 편집
-   템플릿 변경이 기존 문서에 자동 적용되지 않음

### B. 빈 문서

-   제목 및 본문
-   텍스트 서식
-   문단 작성
-   이미지 삽입
-   일반적인 문서 흐름
-   자유 배치 및 드로잉은 제공하지 않음

### C. 자유 작업 문서

-   텍스트
-   이미지
-   영상
-   오디오
-   YouTube 미리보기
-   자유로운 배치
-   그림 및 드로잉

메모, 자유 캔버스, 레퍼런스 보드는 작업 목적과 기본 도구 구성이 다를 수
있다. 편집 엔진을 공유하더라도 화면과 기본 기능은 작업 유형별로
구분한다.

-   콘텐츠 삭제

-   내부 항목 추가 및 삭제
-   순서 변경
-   스타일 수정

스타일 설정: - 배경색 - 테두리 - 모서리 - 내부 여백 - 글자 크기 및
색상 - 정렬 - 표시 방식

각 컴포넌트의 특성에 맞는 설정만 노출한다.

## 5.7 컴포넌트 프리셋

사용자가 여러 컴포넌트의 조합과 설정을 저장하고 다른 문서에서 재사용할
수 있도록 한다.

컴포넌트 프리셋은 문서 전체 구조를 저장하는 사용자 템플릿과 구분한다.

## 5.8 디자인 프리셋

저장 대상: - 컴포넌트 배치 - 크기 - 간격 - 색상 - 배경 - 테두리 - 글꼴 -
타이포그래피 - 이미지 영역

디자인 프리셋은 시각적 스타일만 저장하고 실제 콘텐츠는 저장하지 않는다.

## 5.9 산출물

1.  템플릿 라이브러리
2.  기본 템플릿 편집 기능
3.  사용자 템플릿 제작 기능
4.  공통 및 특화 컴포넌트 라이브러리
5.  컴포넌트 편집 UI
6.  컴포넌트 프리셋
7.  디자인 프리셋
8.  템플릿 및 문서 독립성 테스트

## 5.10 완료 기준

-   기본 템플릿을 수정하고 원래 상태로 복원할 수 있어야 한다.
-   사용자 템플릿을 생성할 수 있어야 한다.
-   템플릿 수정이 기존 문서 콘텐츠에 영향을 주지 않아야 한다.
-   컴포넌트를 여러 템플릿에서 재사용할 수 있어야 한다.
-   프리셋과 템플릿의 저장 대상이 구분되어야 한다.

# 11. 공통 개발 및 유지보수 규칙

## 11.1 기존 데이터 보호

기존 Blankspace 프로젝트의 데이터를 임의로 삭제하거나 초기화하지 않는다.

보존 대상: - 프로젝트 - 폴더 - 문서 - 문서 ID - 컴포넌트 ID - 이미지 -
파일 - 내부 링크 - 관계 정보 - 설정 - 사용자 지정 템플릿

데이터 구조 변경이 필요한 경우 다음 순서를 따른다. 1. 기존 데이터 구조
분석 2. 변경 영향 분석 3. 백업 4. 마이그레이션 계획 수립 5. 테스트 6.
실제 적용

## 11.2 모듈화

-   각 시스템은 독립적으로 관리한다.
-   한 기능의 수정이 관련 없는 다른 시스템에 영향을 주지 않도록 한다.
-   공통 컴포넌트는 중복 구현하지 않는다.
-   플랫폼별 기능은 공통 창작 기능과 분리한다.
-   편집 엔진과 데이터 저장 계층을 분리한다.

## 11.3 기능 구현 원칙

-   실제 동작하는 기능만 구현 완료로 표시한다.
-   임시 UI와 완성 기능을 구분한다.
-   저장 기능을 검증한다.
-   오류 처리와 실패 상태를 제공한다.
-   기능 추가 전 기존 기능과 중복되는지 확인한다.
-   기능 추가 후 회귀 테스트를 진행한다.
-   사용자가 승인한 설계를 기준으로 구현한다.

## 11.4 단계별 승인

각 Phase 완료 시 다음 내용을 보고한다. - 완료된 작업 - 미완료 작업 -
발생한 문제 - 데이터 변경 사항 - 테스트 결과 - 다음 단계의 영향 - 사용자
승인 필요 사항

사용자 승인 없이 다음 단계의 대규모 변경을 진행하지 않는다.

# 13. 최종 개발 목표

Blankspace는 개인 창작자가 자신의 작업 방식에 맞게 문서와 작업 공간을
자유롭게 구성하고, 창작 자료를 연결하며, 웹과 데스크톱에서 동일한 작업
환경을 사용할 수 있는 통합 창작 플랫폼을 목표로 한다.

-   타임라인 구성
-   게임 플로우 설계
-   이미지, 영상, 오디오 레퍼런스 관리
-   모델링 및 애니메이션 자료 정리
-   프로젝트별 자료 관리
-   문서 간 연결 및 정보 탐색
-   클라우드 저장 및 백업
-   웹과 데스크톱 간 작업 환경 공유
